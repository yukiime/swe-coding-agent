# Phase 3 人工抽查指南

你要做的事：校验机器归因是否可信。每个未resolved例有两列机器意见——`rule`（triage.py规则分类）和`panel`（深读复核）——你逐例读轨迹给出**最终人工判定**。目标≥15例，抽查表已按信息量排好序（logs/triage/review_sheet.md）。

## 操作步骤（每例约5-10分钟）

1. 打开 `logs/triage/review_sheet.md`，从上往下领案例（前面的优先级高：机器意见有分歧的、非空patch的）。
2. 打开渲染好的轨迹 `logs/renders/baseline/<instance_id>.md`（IDE里预览markdown最舒服）。任何时候想重新生成：
   ```
   .venv/bin/python -m analysis.triage --tag baseline --render <instance_id>
   ```
3. 建议的阅读顺序（不必逐字读完全文）：
   - **头部harness事实**：有无patch、测试通过情况——先知道这例死在哪个大分支。
   - **问题原文**：理解要修什么。不用完全看懂，知道涉及哪个模块/函数即可。
   - **快速扫工具调用序列**：只看每轮的 🔧 行，把行为模式扫出来（搜→读→读→测→读……有没有edit？从哪轮开始绕圈？）。
   - **精读两处**：行为转折点前后2-3轮 + 最后3轮（死状态长什么样）。留意"模型说"的content——**它是否嘴上有方案但从未落地成工具调用**。
   - **最后看🔑gold patch**：正确答案改的是哪里，模型读没读到那里。
4. 填表三列：
   - `你的判定`：最终类别key（表头有类别清单）。rule和panel都错就写你认为对的。
   - `备注`：一句话直接死因（自由文本）。**这一列是Phase 4改进方向的金矿，尽量写。**
5. 15例做完后，在表尾"抽查结论"区写2-3句总体观察（机器分类的系统性偏差、最意外的发现）。

## 各类别的验证要点

| 类别 | 你要重点核实的 |
|---|---|
| located_but_no_edit | 它"读到gold文件"是真读到了关键区域，还是只打开过文件没翻到该改的函数？后者请在备注写"实为定位不完整"。另留意：不动手是在等什么（反复确认？没形成方案？content里有方案没执行？） |
| wrong_location | 确认gold文件名在全文确实从未出现在read_file里（cmd+F搜文件名最快） |
| edit_failure_loop / ignored_error_or_repeat | 看每次edit失败后模型有没有先re-read再改参数。有调整=前者，原样重试=后者 |
| broke_other_tests / wrong_fix | 头部harness数字已是事实，你主要判断：patch方向是对的但差一步，还是南辕北辙？写进备注 |
| context_loss | 看它是否重取很早之前拿过的内容、忘记已确认的结论。这类规则只能置旗标，主要靠你确认 |

## 判定原则

- 只选**一个主因**：多因并存时，选"最早把轨迹带进死胡同"的那个。
- 允许推翻机器双方；不确定就在备注里写"存疑+原因"，别硬选。
- 别被gold patch锚定：模型没按gold的路子修不等于错，官方判卷只看测试结果（但空patch没有这个问题）。

## 完成后

告诉我"抽查完了"，我会：汇总你的判定成最终归因表 → 和你确认Phase 4的两个改进方向（候选分析草稿在 analysis/phase4_candidates.md，先别当结论看）。

预计总耗时：15例 × 6-10分钟 ≈ 1.5-2.5小时，可分多次做，表里填到哪算哪。
