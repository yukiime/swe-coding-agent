# Phase 4 改进候选分析（草稿——以人工抽查后的最终归因表定案）

基线事实（50例，官方harness判定）：resolved 20/50=40%。未resolved 30例中：**24例读到了gold文件却0次edit**（其中21例第5轮前就读到，中位数第2轮）、5例有patch但没修对（3例还破坏了已过测试）、1例实际完成了修改但patch被工具链丢弃。

## 前置：工具链bugfix（建议无条件先修，是否单独占一轮全量重跑由你定）

不是"改进"，是修我们自己的bug，三处合计<20行：

1. **patch导出丢新建文件**（loop.py:47）：`git diff`不含untracked文件。astropy-13398实际新建并写入了gold要求的文件，交卷时patch=0字符被静默丢弃（panel双读者high confidence确认）。修法：导出前`git add -A`再`git diff HEAD`。
2. **run_tests吃掉shell语义**（tools.py:113）：`timeout N cd /testbed && ...`中`timeout`无法执行shell内建`cd`，exit=127。**50例中25例踩坑**，未resolved中14例（django-13810踩了8次）——模型想做的快速验证反复被拒，直接助长"不敢动手"。修法：`timeout N bash -c '<command>'`。
3. **edit_file不能创建新文件**：13398被迫用run_tests执行touch绕路2轮。修法：path不存在且old_str为空时直接创建。

直接收益：+1例（13398）；间接收益：归还被浪费的轮次。风险≈0。

## 候选1：行动强制——让模型在预算内动手

- **针对**：`located_but_no_edit`，24/30=未resolved的80%、全部50例的48%，头号失败模式。
- **证据**：定位不是瓶颈（21/24第5轮前读到gold文件）。astropy-8707第7轮已在content里说出与gold一致的修法，之后13轮继续"确认理解"；django-11087最后三轮反复分段重读同一文件至死。模型不知道自己还剩几轮，把20轮当无限用。
- **机制**（loop.py+system_prompt，约15-30行）：
  a. 每轮注入轮数预算：`[Turn k/20]`；
  b. 看门狗：连续N轮（如4轮）无edit_file时注入硬提醒："你已读过目标代码，本轮必须给出最小修改，禁止继续只读"；
  c. system prompt加军规：最晚第8轮必须产出第一个edit，改错可以再改。
- **预期提升**：非空patch的基线resolve率80%（20/25），但这24例偏难需打折——按转化率50%×成功率50%估算 **+6例（40%→52%）**；保守+4，乐观+10。
- **风险**：逼太紧可能催生乱改（broke_other_tests上升）——对比时盯住P2P回归数。

## 候选2：上下文记忆强化——截断不丢结论

- **针对**：`refetch_after_trim`旗标17/30例；panel在django-13012判定context_loss为主因（与规则分歧，待你抽查裁决）；同时是候选1的放大器（模型忘掉已读内容→更不敢动手）。
- **证据**：13398因截断重读浪费3轮，直接导致gold必需的`__init__.py` import没来得及做；11087后半程重读区间与被滚出窗口的前期读取完全重合；24例no_edit中14例有此模式。
- **机制**（context.py，约30-50行）：滚动截断时不再整轮丢弃，改为保留每轮assistant的content（方案陈述）只丢工具输出；或维护一份"已读文件+已确认结论"清单pin在system之后每轮更新。
- **预期提升**：单独 **+2~4例**；与候选1叠加时提高其转化率（先动手+不失忆）。
- **风险**：改动所有例的上下文结构，可能有全局性副作用；token成本略升。

## 建议的两轮安排（待讨论）

- **Round 1 = 工具链bugfix + 候选1**：bugfix几乎零风险可捆绑，候选1是最大杠杆。若你想严格归因，也可以Round 1只修bug（重测出"诚实基线"），候选1挪Round 2、候选2转Phase 5消融——取决于你想要"最大提升"还是"最干净归因"。
- **Round 2 = 候选2**（或候选1，视Round 1选择）。
- 成本参考：全量重跑一轮≈$0.75（¥5.5左右），两轮在余额内。
